# ToSleep MVP 产品需求文档（PRD）

- 版本：v0.1（2026-11-02）
- 平台：Android（React Native 0.88 + Kotlin 原生模块）
- 包名：`com.sera.tosleep`
- 状态：核心功能已在代码中实现（见 [DOCS.md](../DOCS.md)），本文档定义 MVP 的范围、验收标准与上线前必须补齐的缺口

---

## 一、产品概述

### 1.1 一句话描述

ToSleep 是一款 Android 睡眠守护应用：到设定的入睡时间自动把手机锁定为"只能看时间"的 kiosk 模式，到起床时间自动解锁，帮助用户切断睡前刷手机。

### 1.2 解决的问题

睡前刷手机是普遍的入睡拖延行为。市面上的专注类 App 依赖用户自觉手动开启，在"最需要约束的时刻"（躺在床上、意志力最弱时）恰恰失效。ToSleep 的差异点是**每日定时 + 静默强制锁定**：无需用户当下做出决定，到点即锁。

### 1.3 目标用户

- 想改掉睡前刷手机习惯、但自控力不足的人（核心）
- 为孩子管理设备使用时间的家长（潜在延伸，MVP 不做）

## 二、MVP 功能范围

### 2.1 必须有（MVP 核心，均已实现 ✅）

| # | 功能 | 描述 | 代码位置 |
|---|---|---|---|
| F1 | 每日定时锁定 | 到设定的每日开启时间（默认 22:00），App 自动点亮屏幕、回到前台并弹确认窗 | `App.tsx` 轮询 + `WakeAlarmModule.kt` 精确闹钟 |
| F2 | 确认弹窗 | 锁定前弹窗告知"锁定至几点"，用户点"开始锁定"确认 | `App.tsx` confirm modal |
| F3 | 贪睡（有限延迟） | 每晚最多 3 次、每次 5 分钟的延迟；次数耗尽后弹窗不可关闭，只能锁定 | `SNOOZE_MINUTES` / `MAX_SNOOZES` |
| F4 | Kiosk 锁定与自动解锁 | 进入 Lock Task Mode，倒计时到每日关闭时间（支持跨天，如 22:10→06:30）后自动退出 | `KioskManager.startKiosk/stopKiosk` |
| F5 | 熄屏唤醒 | 熄屏后 JS 定时器不可靠，由 AlarmManager 精确闹钟唤醒屏幕并拉起确认窗 | `WakeAlarmModule.kt` + `WakeAlarmReceiver.kt` |
| F6 | 设置持久化 | 每日开启/关闭时间可调（±5 分钟步进），存原生 SharedPreferences，重启保留 | `WakeAlarm.getSettings/setSettings` |
| F7 | 开机自启动 | 设备重启后自动拉起 App，保证定时逻辑不失效 | kiosk-manager `BootReceiver` |
| F8 | 手动锁定 | 首页"立即开始专注"按钮随时手动进入锁定 | `App.tsx` |

### 2.2 明确不做（Non-goals，MVP 阶段）

- ❌ iOS 版本（Lock Task Mode 为 Android 专属能力）
- ❌ 使用统计 / 睡眠报告图表
- ❌ 锁定期间应用白名单（kiosk 模式下完全无法使用其他 App）
- ❌ 多套时间计划（工作日/周末区分）
- ❌ 远程管理、家长端、多设备同步（无后端）
- ❌ 解锁密码 / 紧急解锁（MVP 依赖系统设置强制停止 device owner，见风险）
- ❌ 非强制模式（MVP 定位就是"硬约束"，不做纯提醒模式）

### 2.3 用户故事与验收标准

**US1 — 每晚自动锁定**
> 作为用户，我设置开启 22:00 / 关闭 23:00。22:00 时无论手机在做什么（熄屏、其他 App），屏幕自动亮起并弹出确认窗。

验收：
- [ ] 熄屏状态下到点屏幕点亮并弹出确认窗（F5 生效）
- [ ] 在其他 App 前台时，ToSleep 被拉回前台
- [ ] 精确闹钟权限未授予时不崩溃，触发允许延迟（降级日志可见）

**US2 — 有限贪睡**
> 我还没睡意，点"再睡 5 分钟"，弹窗消失 5 分钟后重现；最多 3 次后弹窗无法关闭。

验收：
- [ ] 贪睡后闹钟重排到 +5 分钟，弹窗按时重现
- [ ] 第 3 次耗尽后弹窗无"暂不锁定"/"再睡"按钮，返回键失效
- [ ] 跨天后贪睡次数自动重置为 3

**US3 — 锁定与自动解锁**
> 点"开始锁定"后进入 kiosk，无法退出；到关闭时间自动解锁，且当晚不再重复弹窗。

验收：
- [ ] 锁定期间 Home/返回/最近任务均无法离开 ToSleep
- [ ] 关闭时间跨天时（如 23:50 开、07:00 关）时长正确计算到第二天
- [ ] 倒计时结束自动 `stopKiosk()`，恢复系统正常使用
- [ ] 确认锁定后同一天不再弹出确认窗

**US4 — 设置持久**
> 我修改开启时间为 22:30 并保存，重启手机后设置保留且 22:30 正常触发。

验收：
- [ ] 设置保存后立即重排原生闹钟
- [ ] 重启 App / 重启设备后设置值不丢失
- [ ] App 未启动过设置时使用默认 22:00–22:15

## 三、依赖与前置条件（部署要求）

MVP 上线/演示前，目标设备必须完成：

1. **Device owner 配置**（一次性，安装后执行）：
   ```bash
   adb shell dpm set-device-owner 'com.sera.tosleep/com.riuhou.kioskmanager.DeviceAdminReceiver'
   ```
   未配置时 `startKiosk()` 会弹系统确认框，且无法静默拉起 App，US1/US3 大部分验收项不成立。
2. **精确闹钟权限**（Android 14+）：
   ```bash
   adb shell appops set com.sera.tosleep SCHEDULE_EXACT_ALARM allow
   ```
3. **发行包**：面向真实用户分发时无法预配 device owner（需 ADB），MVP 的现实交付形态是**指导用户自行 ADB 配置**（见六、风险）。

## 四、上线前必须补齐的缺口（P0）

以下问题不解决，不能视为可交付的 MVP：

| # | 缺口 | 现状 | 要求 |
|---|---|---|---|
| G1 | node_modules 本地补丁未固化 | kiosk-manager 的补丁直接改在 node_modules 里，`yarn install` 即丢失 | 用 patch-package（或 yarn patch）固化并提交到仓库 |
| G2 | 调试残留 | 首页右下角"End"按钮可随时解锁，等于绕过全部约束 | 移除，或仅在 debug 构建中保留 |
| G3 | Release 签名 | release 构建尚未配置正式签名 | 配置签名；device owner 的 APK 签名在配置后不可更换，需用最终签名密钥部署 |
| G4 | 大量 `console.log` 调试日志 | 轮询每次都打日志 | 清理或降为 `__DEV__` 条件输出 |

## 五、P1（MVP 之后第一批迭代）

1. 锁定页面 UI：当前锁定后仍是普通首页 + 倒计时，应有专用锁定画面（大时钟、熄屏提醒）
2. 应用白名单：允许锁定期内使用电话、时钟等白名单应用（`setPermittedActivities`）
3. 首次引导：检测 device owner / 精确闹钟权限状态，引导用户完成配置
4. 周末/工作日差异化时间表
5. 简单使用统计（本周锁定次数、贪睡次数）作为习惯反馈

## 六、风险与开放问题

| 风险 | 影响 | 缓解 |
|---|---|---|
| Device owner 需要 ADB，普通用户无法自行完成 | 直接限制目标用户群为"有技术能力或愿意照教程操作的人" | MVP 文档化安装教程；P1 做应用内引导；长期考虑托管配置（QR 码 provisioning） |
| 无紧急解锁手段，设备故障时用户被锁死 | 差评/信任风险 | 文档写明 `adb shell dpm remove-active-admin` + wipe 退出路径；P1 增加"紧急解锁需输入长密码" |
| kiosk-manager 为第三方库且需本地补丁 | 升级 RN 时可能编译失败 | G1 固化补丁；考虑 fork 仓库 |
| 精确闹钟在部分厂商 ROM（Doze 激进策略）下延迟 | 触发不准 | 前台 20 秒轮询兜底已存在；真机测试列入验收 |
